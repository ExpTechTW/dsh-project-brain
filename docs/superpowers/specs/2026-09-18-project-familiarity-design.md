# Project Familiarity（兩套檢視、一份資料）

Date: 2026-09-18  
Status: Spec (not implemented)  
Grill: [`.grill/project-familiarity.md`](../../../.grill/project-familiarity.md)  
Does not replace: [2026-09-15-durable-core-memory-design.md](./2026-09-15-durable-core-memory-design.md)

## 1. Goal

外掛隨長期開發越來越熟悉**這一個專案**。新手開啟專案 Tab 就能動手；老手能順著從建倉以來的主幹看到「做了什麼重要開發、改了什麼」；新 Session 的 Agent 拿到與人同一份 briefing，再加上 Core 站立事實，像同一名從業者接著幹。

熟悉的主體是 **人 + Agent 同一條開發線**，不是一份越堆越大的知識庫，也不是聊天回放。

**Winning condition**

1. 未讀過倉庫的人，看第一屏四句話後知道改哪、卡在哪。  
2. 新 Session 不介紹專案，模型第一輪能點到 briefing 裡的入口/關鍵檔案，且不重開已結算決策。  
3. 「任務動態」能從 `init` 順著 Session 主幹走到現在；點開節點能看到人話摘要和檔案證據。

## 2. Non-negotiables

- 一份 `.project-brain/`，不新造編年史檔案、不把聊天原文入庫。
- Durable Core 閘門全部保留：`admitMemory` 單寫者、changelog 不進 Core、Core 硬頂 15 / ~800 token、禁止 Jaccard merge-and-drop。
- 人 Tab 與 Agent 注入的 briefing **同一組裝函式、同一欄位**；禁止兩套文案各寫各的。
- 擠佔 token 時先截斷 briefing 的「最近為什麼」，**不截斷、不靜默丟 Core**。
- LLM **不得**編造 Session 之間的因果邊。
- 架構過期不得假裝確定。
- 向量檢索仍不是續接主路徑。
- 未初始化專案：不寫記憶、不寫假 timeline 節點、不注入。

## 3. Two views

| 檢視 | 給誰 | 讀什麼 | 不讀什麼 |
| --- | --- | --- | --- |
| Briefing + Core | 人第一屏 + 每次 Agent 注入 | 見 §4、§5 | git 全量、dormant 全量、泳道全圖、聊天 |
| 架構 Tab | 人（第二層） | `architecture.json` 分層/路徑 | 不進第一屏、不整圖注入 |
| 任務動態主幹圖 | 人（第二層） | 由 timeline/todo/memory **派生**的 Session 圖 | 聊天、工具軌跡 |
| Git Tab | 人（證據） | 提交時間線 | 不當主史、不進注入 |
| `project_ask` | 人/Agent 按需 | Core + dormant（及既有 timeline 檢索） | 不自動灌進每個 prompt |

## 4. First screen（專案 Tab / 概覽）

只回答四句。多了的進其它 Tab。

| # | 問題 | 資料來源 | 展示上限 |
| --- | --- | --- | --- |
| 1 | 這是什麼 | `project.name` + 淨化後 description（截斷）+ 執行時技術棧 chip | description ≤ 300 字 |
| 2 | 從哪改 | 見 §4.1 | 入口 1 個優先 + 關鍵檔案 ≤ 5 |
| 3 | 現在卡在哪 | `in_progress` 優先，否則最高優先順序 pending TODO | ≤ 3 條 |
| 4 | 最近為什麼 | 最新一條非空 `session_summary.summary`；否則最新 Core `decision` 的 title+一句 content | 摘要截斷與注入共用預算 |

完整泳道、目錄樹、dormant、Git 全史、匯入匯出按鈕保持現有能力，但 **不得擠掉這四句的主視野**。

### 4.1 「從哪改」

正常（架構未過期）：

- `project.entrypoints` 去重後最多 2 個  
- `architecture.keyFiles` 或等價欄位（見現有 `architecture.json` 的關鍵檔案列表）最多 5 個，路徑相對倉庫根  
- 可選：主執行路徑 **第一步和最後一步** 的檔案，計入 5 個名額，不畫整條編號箭頭

過期（§6）：不用舊泳道當真理。改為 scanner 入口 + `project.json` 已有 entrypoints；UI 與注入都帶 `architectureStale: true` 及一句「架構可能過期」。

## 5. Shared briefing（注入 = 第一屏的 markdown 形態）

單一純函式（建議名 `buildProjectBriefing(brain, options)`），產出：

```ts
{
  stale: boolean,
  purpose: string,          // 這是什麼；scanner 佔位符 Auto-generated by … 視同為空
  startHere: string[],      // 從哪改，相對路徑（只進注入）
  stuck: { id, title, status, priority }[],   // 活躍待辦，in_progress 優先，≤3
  recentWork: string,       // 最近做什麼（可空）
  recentWorkSource: "session_summary" | "todo" | "none",
  recentWorkAt: number,     // 該摘要的 occurredAt；todo 兜底為 0，不許編時間
  recentWorkStale: boolean, // 超過 30 天
  markdown: string          // 人/Agent 共用的 markdown
}
```

`buildInjectionContext(brain)`：

```text
## Project Brain
### 這是什麼 / ### 最近做什麼 / ### 從哪改   ← briefing.markdown
### 活躍待辦            ← briefing.stuck，空則整段不出現
### Core 記憶           ← 現有 isCoreMemory 全量，硬頂仍由 admit/housekeep 保證
### 專案記憶約定
```

人第一屏只看「這是什麼 / 最近做什麼」；「從哪改」與「活躍待辦」只進注入。

**「最近做什麼」必須帶時間。** 不帶時間的近況會騙人：LLM 關掉幾週後，第一屏還在拿舊摘要冒充近況。markdown 字尾「N 天前」，超過 30 天寫「N 天前，可能已過時」。todo 兜底沒有可靠時間戳，就不顯示時間。

**活躍待辦單獨成段。** 續接靠 TODO，既不能混進「最近做什麼」（pending 待辦不是最近做的事），也不能只在「記憶約定」裡空口叮囑。

`project_continue.data.injection` 必須與 injector `section.render` **位元組級一致**（沿用 Durable Core 契約）。

Briefing 獨立預算：`recentWork` 沿用現有 `SUMMARY_MAX_TOKENS = 400`。Core 預算仍是條目 cap，不是再截 briefing。

## 6. Stale architecture + two-tier refresh

在 `project.json` 或 `architecture.json` 記錄：

- `architectureAnalyzedAt`  
- `architectureHeadFilesFingerprint`（相關檔案集合的指紋，不必存全量 blob）

**過期判定：** 當前工作區相對上次架構分析，`architectureTriggerFiles`（§6.1）有變更。輕掃成功 **不** 清除過期；只有 LLM/本地架構重分析成功才清除。

### 6.1 觸發檔案（收緊現狀）

現狀 `architectureRelevantFiles()` 把 README 也算進去，**本 spec 要求拆開**：

| 函式 | 命中 | 用途 |
| --- | --- | --- |
| `sourceChangeFiles(files)` | 原始碼副檔名（現有 `SOURCE_EXTENSIONS`），排除 generated/vendor | 輕掃 |
| `architectureTriggerFiles(files, { changes, entrypoints })` | **結構化規則，不得硬編碼任何倉庫的具體路徑**：① manifest（現有 `MANIFEST_NAMES`）與 `cordis.patch.yml`；② `project.json.entrypoints` 裡宣告的檔案入口（`type: "script"` 的 npm 指令碼不算）；③ 約定入口檔名 `index`·`main`·`app`·`server`·`mod`·`lib`·`__init__`·`__main__` + 原始碼副檔名；④ 原始碼檔案的**增刪**（`changes[].type` 為 `added`/`removed`）。**排除** README、CHANGELOG、lockfile、測試、generated/vendor，以及普通原始碼的「改內容」 | LLM/本地架構重分析 |

純測試路徑啟發式：`/(^|\/)(?:test|tests|__tests__|spec|specs)(\/|$)/i` 或 `/\.(?:test|spec)\./i`。

「改一行 UI 就跑一次 LLM 架構」和「換個專案就永遠不重新整理架構」是同一個錯誤的兩面：規則必須由 manifest / 宣告入口 / 檔案增刪這類**結構訊號**決定，不能靠列舉某個倉庫的目錄名。寧可漏觸發，也不要不可移植。

### 6.1.1 會話變更視窗

`files` 不再取 `HEAD vs HEAD~1`。`detectSessionChanges({ projectPath, sinceMs, now })`（`src/host/diff/session-window.js`）合併兩路：

- 工作樹中 mtime 落在 `(sinceMs, now]` 的檔案——**未提交的改動也算**，非 git 專案同樣可用；
- `committer` 時間落在視窗內的 commit（上限 30 個），逐個與 first parent 做 tree diff。

視窗起點 `sessionWindowStart(brain, now)` = 上次 `session_summary.occurredAt` > `project.lastScannedAt` > `project.createdAt` > 24 小時前，且最長只回看 14 天。輸出 `changes: [{ path, type }]`，`type ∈ added | modified | removed`。

### 6.2 Session 結束（`summarizeOne` 之後）

順序：git diff → 語義抽取/admit → 寫 `session_summary` → housekeep → **重新整理**（失敗只打日誌，不阻塞 disposed）。

1. `sourceChangeFiles` 非空 → `scanAndWrite(..., { architectureMode: "light" })`：只更新 `project.json` 掃描欄位（入口、技術棧、語言），**保留**現有 `architecture.json`。  
2. `architectureTriggerFiles` 命中 → 再 `scanAndWrite(..., { architectureMode: "full" })`。  
3. **觸發了就必須給出結論**：full 成功且 `architecture` 無 error → `architectureStale = false`（由 `scanAndWrite` 寫入）；full 失敗或架構帶 error → 用 `markArchitectureStale(fs, policy, projectPath, true)` 顯式置 `architectureStale = true`，只改標記不碰 `architecture.json`。輕掃不改該標記。

使用者手動 `project_rescan` / 第一屏「重掃」= `architectureMode: "full"`。

## 7. `session_summary` 合同

寫入 `timeline.jsonl`，`eventType: "session_summary"`。

**正文 `summary`：** 1–3 句，做什麼重要的 + 為什麼。禁止 changelog 體裁（「改了 N 個檔案」、驗收清單、patch 標題）。與 `isChangelogGenre` / `isActivityReport` 同一套否決；命中則 `summary` 置空並記 `summaryRejected: "changelog_genre"`。

**附件（可進節點展開，不進注入）：** `changedFiles` 最多 20 條相對路徑（現有 detail 字串不夠用，本 spec 要求結構化欄位 `files: string[]`）。

抽取失敗或 transcript 太短：仍可寫 timeline 行以便去重 `sessionId`，但 `summary` 為空。圖與 briefing **視為無摘要**。

關會話沒留下非空摘要、也沒「記住」、也沒 admit 成功：talk-only 回合在史上等於沒發生。

## 8. Development chain graph

不新增 json 檔案。每次 preview / RPC 由純函式 `buildSessionGraph(brain)` 從已有 jsonl 派生。

### 8.1 節點

一個節點對應一次 `sessionId`。無 `sessionId` 的實質事件（`session_summary` / `todo` / `memory` / `memory_supersede`）按發生日合成 `day:YYYY-MM-DD` 桶，使舊時間線仍能成幹。`init` 可合成 `sessionId: "init"`。`rescan` / `export` / `import` / `rollback` 不成節點。

**進入主幹（`trunk: true`）當且僅當至少一條：**

- 非空且未 reject 的 `session_summary.summary`  
- 該桶關聯的 git `files.length > 0`  
- 該桶有 TODO 狀態變化，或非 changelog 體裁的 memory  
- 純 changelog 體裁記憶、僅重掃/匯入匯出、空摘要且無檔案：不進主幹，計入 `collapsedEmptyCount`

節點展示：

- `label`：優先 `summary` 第一句（切句時保護 `v0.4.13` 這類版本號，不當句號）；否則該桶內非 changelog、非補丁體裁的 memory/todo 標題（去掉「新增記憶/待辦」字首）；否則 `程式碼有變更（無摘要）`（僅當有 files）。  
- `detail`：展開區正文。取摘要第一句之後的餘句，否則取該桶記憶的 `content`；與 `label` 相同則為空，展開區不復寫標題。**純文本**：展開區不渲染 markdown，`##` / `**` / 反引號 / 列表 / 引用 / 連結語法一律剝掉（只去符號、不丟文字）。上限 900 字，優先在句末斷開，真截斷時結尾必須是 `…`；UI 側可滾動，不做視覺截斷。  
- `files`：最多 5 個展示，其餘 `filesMore`  
- `occurredAt`：桶內**最後一次活動**時間（timeline 與 memory 統一口徑，否則先後會錯）  
- `sessionId`（日桶為 `day:YYYY-MM-DD`）

**補丁體裁判定：** 以版本號開頭**且**後面是補丁/釋出語氣（patch / hotfix / fix / 修復 / 補丁 / 發版 / 驗收 / 改動說明），或版本號後什麼都沒有。只看「開頭是不是數字」會誤殺 `2.0 版本規劃`、`3.2 資料層重構`。

**禁止**用「改了 N 個檔案」當 `label`（與 §7 一致）。無摘要僅有檔案時用固定文案 `程式碼有變更（無摘要）`。

### 8.2 邊

- **主幹邊：** 按 `occurredAt` 排序後相鄰 trunk 節點 `kind: "time"`  
- **證據邊** `kind: "evidence"`，僅三種：  
  1. 同一 `todo.id` 在 a 開啟、在之後的 b 關閉。**只有「開 → 關」算因果**：把 done 事件也當起點，會在重複標記完成時連出假邊。實現用 `todoId → 完成節點下標` 倒排索引，不做全對遍歷。  
  2. `project_memory_supersede` / admit `supersedes` 連線新舊 memory 所屬 session  
  3. `architectureMode: "full"` 的 rescan 事件，`triggerFiles` 與**緊鄰的上一個** trunk 節點 `files` 有交集（不跨節點連遠邊）  

無證據則不要第二條邊。不要 LLM 補邊。

### 8.3 抽稀（預設全自動，不做手動里程碑）

trunk 節點 > 40：隱藏 `important: false` 的節點，**但保底顯示最近 20 個**。只有摘要缺失、歷史全靠記憶標題的專案，一次性藏光會讓預設檢視幾乎空白，反而更像"斷開"。其餘進「展開全部」。節點本身不刪。不按周合併（避免把因果邊弄斷）。手動釘版本節點 **本版不做**。

### 8.4 UI

升級現有 **任務動態** Tab：上半主幹圖（時間從左到右或從上到下），下半可保留 TODO 列表。Git Tab 不變。點節點：摘要全文 + 檔案列表 + 跳 Git 不強制。

## 9. Out of scope

- 聊天原文 / 工具呼叫回放  
- LLM 專案編年史、無證據因果  
- 第一屏或注入塞滿泳道/目錄/全史  
- 跨專案聯邦、再擴 AST、替代 Jira  
- 每輪對話一個圖節點  
- 手動里程碑釘選（可後加）
